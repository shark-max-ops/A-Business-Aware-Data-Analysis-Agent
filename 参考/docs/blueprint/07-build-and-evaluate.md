# 07 实施顺序、验收与评估

## 1. 总体方式

每阶段完成一个能运行的纵向路径，再进入下一阶段。开发 AI 每次先读契约和已有实现，避免一个会话生成后端、另一个会话重新发明不同字段。阶段之间更新根目录 `IMPLEMENTATION_STATUS.md`：已实现、未实现、实际执行的命令、检查结果、已知限制。

以下命令是目标接口，在对应阶段实现后运行。没有实现前，不把它们列成“已验证”。

## 2. 阶段 0：建立可运行工程

交付：Python 包、FastAPI health、SQLite/Alembic、React 三页壳、统一 DTO/错误模型、配置、锁文件、gitignore、小型 fixture。

验收：`uv sync`、迁移、后端启动、`npm ci`、前端 build；缺少模型密钥仍可打开页面并看到未配置状态。根 README 给出 Windows PowerShell 启动命令。

可以交给 AI 的任务：

```text
只实现阶段 0。遵守 01 的目录和 06 的错误契约。
创建 health 与三个页面导航，建立 SQLite 迁移和配置。
使用明确 empty state，不以静态示例数据伪装真实后端结果。
运行基本启动检查和前端构建，更新 IMPLEMENTATION_STATUS.md。
```

## 3. 阶段 1：先完成数据库与受限查询

交付：fixture 导入、真实 BTS CSV 导入 CLI、manifest、数据质量报告、DataSnapshot、业务视图、SQL guard、子进程执行器、QueryArtifact。前端数据源抽屉可查看真实表结构；此时不必已有 LLM。

验收：真实 DuckDB 聚合返回已知结果；取消/备降/负延误/null/多条 SQL/外部读取/超时均有测试；未允许 SQL 不落到执行器；查询超时不留下子进程；换快照不覆盖旧文件。

目标：`uv run python -m metric_pilot.data.ingest --input ./data/bts.csv --period 2026-01`。

## 4. 阶段 2：知识、Wiki 和指标

交付：Markdown/TXT 导入与版本、FTS5 + embedding、来源定位、Wiki 草稿/编辑/发布/回滚、结构化指标 v1。先使用 5—8 份精简材料，不做数百 PDF。

验收：能从中文问题找到相关英文术语来源；无效引用被拒绝；生成不会覆盖人工修改；生效期和冲突处理明确；旧 revision 可读。embedding 未配置时文本检索可单独用，但 UI 标记实际模式。

## 5. 阶段 3：Agent 与工具事件流

交付：LLM adapter、ToolRegistry、Runtime、上下文预算、错误恢复、Job/Run 状态、SSE 重放。先让 FakeLLM 完成真实的“指标 → 结构 → SQL”流程，再接真实模型。

验收：多工具调用消息配对；16 轮/24 调用/总 deadline 能终止；无效参数可反馈修复；重复失败有限；空结果正常；取消/重启/断线都有准确状态。

不把预置 SQL 直接按问题关键词命中作为 Agent 正常路径。指标 SQL 模板可以存在，但自由分析仍通过模型选工具与参数完成。

## 6. 阶段 4：可追溯报告

交付：ReportDraft 校验、ValueRef 物化、KPI/表/图/文字块、EvidenceDrawer、immutable ReportRevision、报告列表。

验收：数值来自真实查询；伪造 ID、跨 run、越界列、截断结果被拒绝；百分比不重复乘百；旧报告不随数据或规则更新改变；失败 run 不生成成功报告卡片。

## 7. 阶段 5：评估与可演示交付

交付：人工核对的问题集、基线与改进结果、典型失败分析、真实模型成本/耗时、小型 fixture 演示、完整 README、架构图和演示录像。

真实全量数据和远程模型的结果不可由 fixture 结果替代。缺少 API Key 时说明未运行哪些评估，不编造提升百分比。

## 8. 评估集设计

建议 40 个标准问题：10 个基础查询、10 个口径敏感问题、8 个组合分析、6 个无法回答/需澄清问题、6 个恢复与边界问题。另建 SQL 防护与证据完整性测试，不与问答分数混为一谈。

从中划分开发集和未参与调参的测试集；即使规模小也记录划分，不拿反复调试的同一批问题声称泛化结果。

每道题包含：

```yaml
id: arrival_deviation_vs_delay_01
question: 比较本月各航空公司的平均到达偏差与平均非负延误
snapshot_manifest: 实际固定清单路径
knowledge_snapshot: 实际固定知识版本清单
expected_metric_keys:
  - mean_arrival_deviation
  - mean_nonnegative_delay
required_sources:
  - 实际指标定义修订ID
gold_sql_file: gold/arrival_deviation_vs_delay_01.sql
checks:
  - same_population
  - numeric_tolerance
  - evidence_resolves
expected_behavior: answer
```

Gold SQL 由开发者结合指标定义审阅，再在固定快照执行。不能用被评估 Agent 生成的答案直接当 gold。数值比较先按业务键对齐，再按类型设容差；没有 ORDER BY 的结果不按偶然行顺序判错。空值和零分开。

## 9. 对照实验

在同一模型、同一快照、相近工具预算下比较：

| 配置 | 目的 |
| --- | --- |
| A：仅 schema + SQL 工具 | 测量不带业务知识的基础能力 |
| B：A + 原文检索 | 测量业务资料检索的收益 |
| C：B + Wiki 与结构化指标 | 测量知识整理和指标约束的收益 |

执行恢复可另做开启/关闭的独立实验，避免多项同时改变后无法解释原因。固定模型参数和 provider 版本信息；服务端不支持 seed 时如实记录。真实运行至少保留逐题记录，有成本允许时重复运行观察波动。

指标建议：

- 查询可执行率：合法问题中产生成功查询的比例。
- 数值正确率：结果与 gold 按键对齐后的正确率。
- 口径遵守率：使用正确人群、分母、阈值和时间范围的比例。
- 引用完整率：可解析引用覆盖应有依据的结构化结论的比例。
- 来源支持率：抽样人工判断引用是否真正支持解释，区别于 ID 存在。
- 正确澄清/拒答率：对材料不足或歧义问题的预期行为。
- 延迟、调用次数、token 和估算费用；费用按实际 provider 计价，不硬编码未核实价格。

Wiki 不一定提升每道题。若 C 不如 B，分析错误来源，如摘要丢失范围、检索偏向生成文本、规则版本错误；不要为了简历删除失败样例。

## 10. 关键小型 fixture

至少覆盖：提前到达、恰好 15 分钟、14 分钟、正常 0 分钟、取消、备降、缺失 arrival_delay、null 原因分钟、零分母、机场维表重复键候选、两个不同航空公司、至少两个日期。

用人工可算的小数据给出 gold。例如 3 个 eligible arrivals 的 arrival_delay 为 -10、0、20，则平均偏差为 10/3，非负平均为 20/3，延误率为 1/3。加入取消记录后，eligible 分母不变，计划航班与取消率分母变化。

## 11. 完成版交付检查

- 从全新目录按 README 能安装、迁移、导入并启动。
- 三个主页面都有真实数据路径和明确空状态。
- 一次真实模型演示完成：规则检索 → SQL → 报告 → 点击数字看证据。
- 一次失败恢复演示，一次无法回答演示，一次 Wiki/规则更新后旧报告不变的演示。
- 对照实验、失败案例和已知限制公开可核对。
- 来源与许可证说明齐全；复用 DB-GPT 代码保留应有声明。
